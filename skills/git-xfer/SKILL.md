# git-xfer — перенос коммитов между несвязанными репозиториями

CLI `git-xfer` переносит коммиты между двумя репозиториями без общей истории.
Профиль в его конфиге — это **пара** репозиториев; направление задаётся флагом
`--to a` / `--to b`.

## 0. Убедиться, что инструмент есть и настроен

Пропусти этот раздел, если `git-xfer --version` уже отвечает.

### Установка

```bash
command -v git-xfer && git-xfer --version
python3 --version              # нужен 3.11 или новее
```

Нет команды — поставь из репозитория `StasPotapov/git-xfer`. Он открытый,
доступ не нужен. **Спроси, куда ставить и каким способом** — это изменение
окружения человека:

```bash
# способ 1 — прямо из репозитория, если есть uv или pipx
# (они фиксируют интерпретатор):
uv tool install git+https://github.com/StasPotapov/git-xfer

# способ 2 — клон и симлинк, без установки:
git clone https://github.com/StasPotapov/git-xfer.git <куда>
mkdir -p ~/.local/bin && ln -s <куда>/bin/git-xfer ~/.local/bin/git-xfer
```

После симлинка проверь, что каталог виден: `command -v git-xfer`. Пусто —
значит `~/.local/bin` не в `PATH`, скажи об этом человеку.

Совсем без установки работать можно из каталога клона:
`python3 -m gitxfer ...` или `<клон>/bin/git-xfer ...`. Файлы пакета
напрямую (`python3 gitxfer/cli.py`) не запускай — так нельзя.

Зови **через дефис** — `git-xfer`. Форма `git xfer` через пробел тоже
работает, но зависит от того, как git разрешает подкоманды.

### Подключить скилл, чтобы в следующий раз хватило одной команды

Если ты читаешь этот файл по ссылке, а не из `~/.claude/skills`, —
**предложи человеку подключить его**, чтобы дальше не давать ссылку
каждый раз. Спроси: это его окружение.

```bash
mkdir -p ~/.claude/skills
ln -s <клон>/skills/git-xfer ~/.claude/skills/git-xfer
```

Симлинк, а не копия: обновляется вместе с `git pull` в клоне. После этого
скилл зовётся как `/git-xfer`. Ставили через `uv tool install` и клона
нет — скажи, что для этого нужен клон, и не клонируй молча.

### Конфиг

```bash
git-xfer status -p <любой> --to b    # покажет, читается ли конфиг
```

Конфига нет (`конфиг не найден`) — создай шаблон и заполни:

```bash
git-xfer init                        # ~/.config/git-xfer/config.toml
```

**Профиль — это ПАРА репозиториев, а не направление.** Направление
выбирается при вызове флагом `--to`. Спроси у человека пути к двум
репозиториям и ветки, потом впиши:

```toml
[profiles.myproj]
a = "/путь/к/первому"
b = "/путь/ко/второму"
branch = "master"          # одна ветка с обеих сторон
# a_branch / b_branch — если ветки называются по-разному
```

**Если проект лежит в подкаталоге одного из репозиториев** — в монорепо
он в `apps/mobile`, а во втором репозитории то же самое лежит в корне —
это отдельный ключ, а не отдельный профиль:

```toml
[profiles.myapp]
a = "/путь/к/монорепо"      # ВСЕГДА корень репозитория
a_prefix = "apps/mobile"    # подкаталог — отдельным ключом
b = "/путь/к/личному"       # тут проект в корне, b_prefix не нужен
branch = "master"
```

Перенос сам срезает `a_prefix` и надевает `b_prefix`, так что лишней
вложенности `apps/mobile/…` в цели не появится. Путь стороны,
указывающий внутрь репозитория, — ошибка: `doctor` покажет готовый
фрагмент, которым профиль переписывается. **Префикс не выдумывай сам:**
если видишь монорепо, а `*_prefix` в профиле нет — спроси человека,
какой подкаталог ему нужен.

Ветка в профиле — заготовка на частый случай, а не единственно возможная:
любой вызов принимает `-b`, `--source-branch` и `--target-branch`. Поэтому
не заводи профиль под каждую ветку и не переписывай ветку в существующем.

**Служебные коммиты не переносить** — если человек об этом просит
(«коммиты со словом „служебный“ не таскай»), это правила `skip`:

```toml
[defaults.skip]                  # для всех пар; у профиля — [profiles.<имя>.skip]
subject = ["(?i)служебн"]        # регэкспы по заголовку
commits = ["a1b2c3d"]            # конкретные хеши
paths = ["*.lock", ".idea/*"]    # коммит, у которого ВСЕ файлы под масками
```

Правила профиля добавляются к общим. Предложи, куда их положить, и покажи
фрагмент до записи.

Заводить профиль не обязательно: разовый перенос делается флагами, вовсе
без конфига.

```bash
git-xfer list --source /путь/a --target /путь/b -b master
```

Конфиг — файл человека. **Не переписывай существующие профили** и не меняй
`[defaults]` без просьбы; добавлять новый профиль можно, показав, что именно
добавляешь.

## Железное правило: только неинтерактивные вызовы

**Каждая команда обязана завершиться сама.** У тебя нет терминала: команда,
севшая ждать ввода, не вернётся никогда — ни ответа, ни ошибки, разговор
просто встанет. Это самый частый способ сломать работу, и виноват тут не
инструмент, а вызов.

`git-xfer` сам себя страхует: интерактивные пути он включает только при
настоящем терминале, а зависший git прерывает по таймауту (`git_timeout`,
по умолчанию 600 с). Но за команды, которые ты зовёшь мимо него, отвечаешь ты.

Давай всё явно:

- направление — `-p <профиль> --to a|b` (либо `--source`/`--target` и `-b`);
- коммиты — `--commits 1,3,5-7` или `--sha <хеш>...`, **никогда** `-i`;
- подтверждение — `--yes` (только после того, как человек сказал «да»).

**Никогда не запускай** — ни у `git-xfer`, ни у git, ни у чего-либо ещё:

| нельзя | почему | вместо этого |
|---|---|---|
| `git-xfer apply --ask`, `apply -i`, `plan -i` | ждут человека у терминала | `--commits` / `--sha` и `--yes` |
| `git commit` без `-m`, `git rebase -i`, `git add -p`, `git mergetool` | открывают редактор | `-m "..."`, правка файла, `git add <файл>` |
| `git cherry-pick --continue` руками | откроет редактор сообщения | `git-xfer continue` |
| `less`, `more`, `man`, `vim`, `nano` | пейджер и редактор держат терминал | `cat`, `head -50`, `git --no-pager ...` |
| `tail -f`, `watch`, `ping`, сервер на переднем плане | не кончаются по своей природе | `tail -80 <файл>` один раз |
| `gh auth login`, `ssh` на новый хост, `sudo` | спросят пароль или подтверждение | попроси человека сделать это самому |
| установка, спрашивающая подтверждение | ждёт `y/n` | флаг вроде `-y`, а лучше — спроси человека |

Git у себя внутри `git-xfer` уже обезврежен: редактор и пейджер
(`GIT_EDITOR`, `GIT_PAGER`), запрос логина и пароля (`GIT_TERMINAL_PROMPT=0`,
`GIT_ASKPASS`) и ssh без `BatchMode` (`GIT_SSH_COMMAND`, только если человек
не задал свой). Свои вызовы git страхуй сам: `--no-pager` для любого
`log`/`show`/`diff`, `--no-edit` там, где git хочет сообщение.

## Если команда не отвечает

Прерви её и разбирайся, а не повторяй ту же самую — второй раз она зависнет
точно так же.

1. **Посмотри, что это было за команда.** Из списка выше — причина найдена,
   зови по-другому.
2. **`git-xfer` встал сам** — загляни в журнал (`tail -80 <путь из status>`):
   последняя строка `git ... → код` показывает, на каком вызове git он стоит.
   Если там `git не уложился` — потолок сработал, и в тексте написано, на чём.
3. **Долго, но не вечно.** На большом репозитории первый `list` считает
   patch-id по всей истории и может занять десятки секунд — это не зависание,
   а работа, и результат кэшируется. Если ждать некогда: `--no-patch-id`
   (исчезнет только пометка `≈`) и `--limit 20`. Второй запуск быстрее.
4. **Целевой репозиторий с git-lfs или хуками** — самая частая внешняя
   причина: lfs лезет в сеть. Скажи об этом человеку, сам с его сетью
   и учётками не разбирайся.

## Коды выхода — читай их, они несут смысл

| код | что значит | что делать |
|---|---|---|
| `0` | успех | дальше по плану |
| `1` | ошибка вызова или конфига | прочитай текст, исправь команду |
| `2` | предполётная проверка не прошла | разбери причину с человеком, **не обходи** |
| `3` | конфликт, серия на паузе | см. раздел про конфликты |
| `4` | ошибка git | загляни в журнал |
| `130` | прервано | ничего не делай |

## Что выяснить до переноса — и дальше не дёргать

Человек хочет одного: сказать, **что** и **куда**, убедиться, что ты понял
правильно, — и чтобы дальше всё сделалось само. Поэтому решения человека
собираются **в два захода**, и второй из них — последний: после него до
самого итога ты больше ни о чём не спрашиваешь.

| заход | когда | что спрашиваешь | дефолт, который предлагаешь |
|---|---|---|---|
| **первый** | сразу после `status` | направление (если из просьбы неясно) и **ветку цели** | ветка — выгруженная сейчас |
| **второй, последний** | после `plan` | одно подтверждение всего переноса (шаг 5) | «да, по одному» |

Раньше `list` про коммиты спрашивать нечего — их ещё не видно; позже `status`
тянуть с веткой незачем — от неё зависят `doctor`, `sync` и сам `list`.

Набор коммитов — не выбор из вариантов, а разбор таблицы, поэтому его
предлагают текстом (шаг 4). Если человек сам назвал коммиты, отдельно
его не обсуждают: набор просто войдёт в подтверждение.

**Подтверждение — это сводка, а не «делаем?».** В нём всё, что случится
с репозиторием человека, и только в нём человек может это поправить:

- откуда → куда: оба репозитория и обе ветки, именами;
- что: хеши и заголовки коммитов, и что про них сказал `plan` (конфликты,
  пустые);
- незакоммиченные правки в цели — «3 файла спрячу в stash и верну после»
  (раздел 1b);
- переключение ветки — «переключу `X` → `Y`, потом верну на `X`»; создание
  ветки — «ветки `Y` нет, создам от `X`» (раздел 1a).

Вопрос — один `AskUserQuestion` с вариантами «Да, по одному», «Да, одним
коммитом» (только если коммитов больше одного; сообщение схлопнутого —
в описании варианта) и «Нет, поправить». Режим схлопывания при этом
отдельным вопросом не идёт — он вариант ответа.

**После «да» — до конца сам.** stash, переключение ветки, `doctor`,
`apply`, конфликты в пределах политики, возврат ветки и правок из stash —
без единого вопроса. Остановиться и спросить можно только когда дальше
идти нельзя или решать не тебе: `doctor` дал код `2` по причине, которую
этот поток не снимает; смысловой конфликт при политике `ask`/`mechanical`;
правки из stash не вернулись чисто.

**Спрашивай только то, чего ещё не знаешь.** Всё, что человек уже сказал —
в самой просьбе, в конфиге, которым он явно попросил пользоваться, или
в ответе минуту назад, — переспрашивать не надо: это не вежливость, а шум.
«Перенеси последний коммит в `release/2.0` одним куском» не оставляет
ни одного открытого вопроса, кроме подтверждения.

Ответы превращаются в флаги вызова, а не в правку конфига:
`--to`, `--target-branch`, `--commits`/`--sha`, `--squash`/`--message`.

Как это выглядит на самой частой просьбе:

> «Перенеси вот этот коммит в `feature/login`»

Ветка названа — не спрашивай её. Коммит один — про схлопывание тоже
спрашивать нечего. В цели выгружена `master`, и в ней две незакоммиченные
правки. Подтверждение:

> Перенос `~/dev/a` (`master`) → `~/dev/b` (`feature/login`): `a1b2c3d fix: …`,
> plan — без конфликтов. В `~/dev/b` сейчас `master` с 2 незакоммиченными
> файлами: спрячу их в stash, переключусь на `feature/login`, перенесу,
> вернусь на `master` и достану правки обратно. Делаем?

После «да»:

```bash
git -C <цель> stash push -m "git-xfer autostash <профиль> <время>"
git -C <цель> switch feature/login
git-xfer doctor -p <профиль> --to b --target-branch feature/login
git-xfer apply  -p <профиль> --to b --target-branch feature/login --sha <хеш> --yes
git -C <цель> switch master
git -C <цель> stash pop --index stash@{N}     # N — найден по метке
```

> «Перенеси эти четыре коммита»

Ветка не названа — спроси её первым заходом. Коммитов несколько — режим
войдёт вариантом ответа в подтверждение.

## Порядок работы

### 1. Понять, что за пара и куда переносим

```bash
git-xfer status -p <профиль> --to <a|b>
```

Покажет направление, ветку цели, путь к state и к журналу, и есть ли
незавершённая серия. **Если серия есть — сначала закончи её** (раздел про
конфликты), новую не начинай.

Если профиль неизвестен — прочитай конфиг (`~/.config/git-xfer/config.toml`,
учитывай `XDG_CONFIG_HOME`) и покажи человеку список пар. Направление не
угадывай: спроси через `AskUserQuestion`, если из просьбы оно не следует
однозначно.

### 1a. Ветка цели — спроси, не бери из конфига молча

**Ветка в профиле — это не приговор, а заготовка.** Коммиты лягут в ту ветку
целевого репозитория, которая сейчас выгружена, и она часто не та, что
записана в конфиге: человек работает в feature-ветке, а в профиле стоит
`master`. Молча коммитить «куда написано в конфиге» — самый обидный способ
испортить чужой день.

Строку `Ветка цели:` печатает `status`: в ней видно и то, что в профиле,
и то, что выгружено сейчас. Дальше — список веток, чтобы было из чего
выбирать:

```bash
git -C <цель> --no-pager branch --format='%(refname:short)' --sort=-committerdate
```

**Спроси через `AskUserQuestion`**, подставив в варианты настоящие имена
веток, а не описания. Порядок такой:

1. **выгруженная сейчас** (`<имя>`) — рекомендуемый: человек в ней и работает,
   и именно в неё коммиты лягут, если ничего не менять;
2. **из конфига профиля** (`<имя>`) — то, что записано в паре;
3. **как в источнике** (`<имя ветки, откуда берём>`) — удобно, когда ветка
   заведена с тем же именем по обе стороны; предлагай этот вариант, когда имя
   отличается от первых двух;
4. **другая** — человек назовёт сам (вариант «Other» в вопросе).

Варианты нередко совпадают именами — тогда не дублируй их в вопросе,
покажи один раз.

Варианты 1 и 2 часто одно и то же имя — **это не повод не спрашивать**.
Вопрос стоит одного экрана, а коммит, уехавший не в ту ветку рабочего
репозитория, стоит человеку вечера. Так что спрашивай **каждый раз**, кроме
двух случаев:

- **ветка названа в самой просьбе** («перенеси этот коммит в `release/2.0`») —
  бери её, не переспрашивай;
- **человек уже ответил на этот вопрос в этом разговоре** — не спрашивай
  второй раз подряд.

В обоих случаях всё равно скажи одной строкой, куда пойдёт перенос:
«переношу в `release/2.0`» — чтобы ошибка всплыла до `apply`, а не после.

Выбранную ветку передавай **явно, каждой команде**:

```bash
git-xfer list -p <профиль> --to <a|b> --target-branch <ветка>
```

`--target-branch` меняет только цель; ветка источника остаётся из профиля.
Нужна другая и у источника — `--source-branch`, обе разом — `-b`.

Флаги ветки — часть адреса: `refs/xfer/*` у такого переноса свои. Значит
и `cleanup` зови с теми же флагами, иначе он скажет «ссылок не найдено»,
а `doctor` потом будет вечно поминать забытые ссылки. Убрать всё разом —
`git-xfer cleanup --all`.

**Если выбранная ветка не выгружена**, `apply` на неё не пойдёт: коммиты
ложатся в выгруженную. Что с этим делать, зависит от того, есть ли ветка
вообще (`git -C <цель> rev-parse --verify --quiet refs/heads/Y`; `doctor`
скажет то же самое):

| что с веткой | что делаешь |
|---|---|
| есть, но выгружена `X` (`doctor`: `сейчас 'X', а нужна 'Y'`) | пункт подтверждения «переключу `X` → `Y`, потом верну на `X`»; после «да» — `git -C <цель> switch Y`, после переноса — `switch X` |
| нет вовсе (`doctor`: `ветки 'Y' в этом репозитории нет`) | **отдельной строкой** в подтверждении: «ветки `Y` нет — создам от `X`, первым коммитом в ней станет перенесённое»; после «да» — `git -C <цель> switch -c Y`, после переноса — `switch X` |

Ни того, ни другого не делай **до** подтверждения — это чужое рабочее
дерево. Создание ветки называй в сводке отдельно и прямо: опечатка в имени
выглядит точно так же, как желание завести новую, и разница видна только
человеку.

Обратно на `X` возвращайся всегда: человек работал там, и его
незакоммиченные правки (раздел 1b) должны вернуться туда же. Грязное
дерево переключению не мешает — stash делается до `switch`.

`plan` можно гнать до переключения: он считает прогноз от ветки цели
из флага, а не от выгруженной.

Ветки `Y` нет — `list` и `plan` с `--target-branch Y` упадут: смотреть ещё
не на что. До подтверждения зови их с `--target-branch X` — новая ветка
пойдёт ровно от `X`, так что и список, и прогноз будут те же. Набор
передавай хешами (`--sha`), а `doctor` и `apply` после `switch -c Y` —
уже с `--target-branch Y`.

Конфиг под выбранную ветку **не правь**. Разовый выбор — это флаг; человек
захочет закрепить — попросит, и тогда это отдельный профиль, а не правка
существующего.

### 1b. Незакоммиченные правки в цели — спрятать и вернуть самому

`doctor` и `apply` требуют чистое дерево цели. Грязное — не повод
останавливаться и гонять человека: правки прячутся в stash на время
переноса и достаются обратно. Отдельно это не спрашивается — это строка
в подтверждении.

**Проверь сразу после `status`**, до `list`:

```bash
git -C <цель> status --porcelain --untracked-files=no
git -C <цель> stash list --format='%gd %s'
```

Первое пусто — прятать нечего, раздел дальше не нужен. Untracked-файлы
не прячь (`-u` без просьбы не ставь): `doctor` на них не блокирует, а
только предупреждает, что перенос может их перезаписать, — это
предупреждение перескажи. Во втором выводе уже есть строка
`git-xfer autostash` — это правки, не вернувшиеся с прошлого раза: скажи
человеку одной строкой и верни их вместе с текущими в конце (или сразу,
если переноса нет). Молча не удаляй.

**Прятать — с меткой**, только после «да»:

```bash
git -C <цель> stash push -m "git-xfer autostash <профиль> <YYYY-MM-DDTHH:MM:SS>"
git -C <цель> stash list --format='%gd %s' | grep -F 'git-xfer autostash <профиль> <время>'
```

Доставать надо **ровно своё**, поэтому ищи по метке, а не голым `stash pop`:
у человека бывают свои stash'и, и `pop` без аргумента вскроет верхний,
каким бы он ни был. По той же причине проверь, что stash создан: на чистом
дереве git ответит `No local changes to save` с кодом `0` и не создаст
ничего — тогда и возвращать нечего.

**Порядок**: stash → `switch` (если нужен) → `doctor` → `apply` → `switch`
обратно (если переключался) → вернуть правки.

**Вернуть** — номер заново найди по метке (он мог сдвинуться):

```bash
git -C <цель> stash pop --index stash@{N}
```

`--index` возвращает и то, что было в индексе (`git add`). Если git
отказался именно из-за индекса (`Conflicts in index`) — повтори без
`--index` и скажи человеку, что staged-разметка потерялась, а правки нет.

**Pop с конфликтом** — перенесённые коммиты правили те же строки, что
и незакоммиченная работа. git оставит stash на месте (`The stash entry is
kept`) и маркеры в файлах. Разбирай по той же политике `resolve_conflicts`,
что и конфликты переноса (раздел «Конфликты»): нижняя половина
(`Stashed changes`) — работа человека, верхняя (`Updated upstream`) — то, что
сейчас в ветке. Если не переключался, это перенесённое; если переносил
в другую ветку и вернулся — это содержимое исходной ветки, а не перенос,
и конфликт тогда не про перенос вовсе. После разрешения и проверки маркеров:

```bash
git -C <цель> reset -q                # снять unmerged и всё, что pop оставил в индексе
git -C <цель> stash drop stash@{N}    # N — снова по метке
```

После конфликта staged-разметка не восстанавливается, даже с `--index`:
правки вернутся, но все — неиндексированными. Скажи об этом в итоге.

**Не коммить** результат — это незакоммиченная работа человека, она должна
остаться незакоммиченной. Политика не даёт решать самому — stash не
трогай, покажи конфликт и жди: правки в безопасности, пока stash на месте.

**Перенос встал на конфликте (код `3`)** — stash не трогай, пока серия
не закончится (`continue` докрутил, `skip` или `abort`); ветку обратно тоже
не переключай — HEAD между паузой и `continue` двигать нельзя. Правки
возвращаются в самом конце.

**В итоге** всегда скажи, что с правками: вернулись; вернулись,
но staged-разметка потеряна; или лежат в `stash@{N}` с меткой — и почему.

### 2. Проверить готовность

```bash
git-xfer doctor -p <профиль> --to <a|b>
```

До подтверждения `doctor` смотрит обстановку, а не выносит приговор: на
грязном дереве и невыгруженной ветке он даст код `2`, и это нормально —
их снимают разделы 1a и 1b. Окончательный `doctor` — после stash и
`switch`, прямо перед `apply`.

Код `2` там — не переноси ничего. Самые частые причины:

- **ветка ≠ настроенной** или **грязное дерево** после того, как ты уже
  переключил и спрятал, — значит, что-то пошло не так: посмотри
  `git status` и не обходи;
- **незавершённый cherry-pick** — см. раздел про конфликты;
- предупреждения (`rerere.enabled`, `core.autocrlf`, сабмодули) не блокируют,
  но перескажи их человеку — они объясняют будущие странности.

### 3. Посмотреть, что можно взять

```bash
git-xfer list -p <профиль> --to <a|b>
```

Таблица: номер, пометка, короткий хеш, дата, автор, заголовок.

| пометка | смысл |
|---|---|
| `+` (U+002B) | новый, не переносился |
| `−` (U+2212, минус, не дефис) | уже перенесён — маппинг в state или трейлер, если он включён |
| `≈` (U+2248) | совпал patch-id: скорее всего то же изменение |

У профиля с префиксом к пометке добавляется вторая — про охват, не про
дедупликацию:

| пометка | смысл |
|---|---|
| `*` (U+002A) | коммит задевает и файлы вне подкаталога — приедет только внутренняя часть |

Ещё одна — про правила из конфига:

| пометка | смысл |
|---|---|
| `×` (U+00D7) | коммит подпал под `skip` (служебный, хеш в списке, только служебные файлы) — по умолчанию не переносится |

**Про `*` обязательно скажи человеку до `apply`**: часть изменения
останется в источнике, и это его решение, а не твоё. Коммиты, не задевшие
подкаталог вовсе, в список не попадают — значит `--limit` считает коммиты
проекта, а не коммиты монорепозитория.

Номера строк — это то, что идёт в `--commits`, и они верны **только при тех же
`--limit` и профиле**. Меняешь `--limit` — перечитывай список. Если ничего
не нашлось, покажи `--limit 100`: окно по умолчанию 30 коммитов.

### 3a. Сравнить и посоветовать, что переносить

Когда просят не «перенеси вот это», а «сравни», «чего не хватает»,
«что стоит перенести» — вместо голого `list` начни с `compare`:

```bash
git-xfer compare -p <профиль> --to <a|b> --target-branch <ветка> --json
```

JSON — всё, на что опирается совет:

| ключ | что это |
|---|---|
| `files` | какие файлы проекта отличаются сейчас: `differ`, `source_only`, `target_only` |
| `missing[]` | коммиты источника, которых нет в цели, newest-first; `number` — тот же, что у `list` |
| `missing[].files` | файлы коммита с `added`/`deleted` строк (`null` — бинарный) |
| `missing[].in_sync` | все его файлы сейчас одинаковы по обе стороны |
| `missing[].after_last_transferred` | новее последнего перенесённого; `null` — границы в окне нет |
| `missing[].overlaps_target_only` | коммиты «только в цели», трогавшие те же файлы |
| `missing[].skipped` | причина, если подпал под правило `skip`; иначе `null` |
| `target_only[]` | что есть только в цели (обратный проход) |
| `warnings[]` | что посчитать не вышло (например, битый state источника) — перескажи человеку |

Дальше посмотри сами изменения. Объекты источника уже лежат в целевом
репозитории, так что всё читается оттуда:

```bash
git -C <цель> --no-pager show --stat <sha>     # на каждого кандидата
git -C <цель> --no-pager show <sha>            # полный дифф — для небольших
```

Что взвесить по каждому коммиту:

- **`in_sync: true` или `≈`** — изменения в цели уже есть (или их позже
  отменили в самом источнике): переносить незачем, станет пустым;
- **коммит и его revert** — пропустить оба; **фиксап к уже перенесённому**
  (`fixup!`, «опечатка в …» сразу после `−`) — брать, иначе цель останется
  с ошибкой;
- **зависимости**: B правит то, что добавил A, — брать вместе и сказать
  об этом; взять только B — почти гарантированный конфликт;
- **специфичное для источника**: CI, адреса и настройки окружения, bump
  версии, файлы, которых в цели нет и быть не должно (смотри
  `files.source_only`) — под вопрос, а не в набор;
- **`overlaps_target_only`** — те же файлы правили только в цели: жди
  конфликта, предупреди заранее;
- **`*`** — приедет только часть, скажи какая;
- **`after_last_transferred: false`** — старая история до последней
  синхронизации, её, скорее всего, пропустили намеренно: по умолчанию
  не предлагай, но упомяни, сколько таких;
- **`skipped`** — не предлагай вовсе, только перечисли одной строкой.

Коммиты «только в цели» переносить не надо — это другое направление. Но
скажи о них: если там правка того же места, что и у кандидата, конфликт
будет, и лучше, чтобы человек знал это до `plan`.

Ответ человеку — три группы, у каждого коммита короткая причина:

```
Берём (4):        3 a1b2c3d fix: …        — исправление, в цели его нет
Под вопросом (2): 5 d4e5f6a ci: …         — правит .gitlab-ci.yml, в цели CI другой
Пропускаем (3):   7 0a1b2c3 ≈ …           — уже есть в цели
Служебные (1):    1 9f8e7d6 × …           — правило skip
```

и готовый выбор хешами — `--sha a1b2c3d …`: он не зависит от `--limit`.
Если человек просил только совета — на этом остановись. Если просил
перенести — дальше обычный путь: `plan` на «Берём» и подтверждение (шаг 5),
где «Под вопросом» стоят отдельной строкой — человек добавит их ответом
«Нет, поправить», если захочет.

### 4. Предложить набор

Разбери таблицу и предложи человеку конкретный набор с обоснованием: что
берём, что пропускаем и почему. Отдельного ответа на набор не жди — сразу
гони на него `plan` и неси в подтверждение (шаг 5): там его и примут или
поправят. По умолчанию бери только `+`. Коммит с `≈`
предлагай, только если человек просит именно его — и предупреди, что он,
скорее всего, станет пустым и будет отброшен.

**Коммит с `×` не предлагай.** Если человек сам назвал такой коммит —
спроси через `AskUserQuestion`: «`<хеш> <заголовок>` помечен служебным
(правило: `<причина>`). Точно переносить?» — и только после «да» добавь
`--include-skipped`. Без флага утилита такой коммит не возьмёт (код `1`),
а `--commits all` пропустит его сама. Правила `skip` в конфиг не дописывай
и не убирай, пока человек не попросит.

Merge-коммиты в списке не показываются и не переносятся. Не добавляй
`--allow-merges` по своей инициативе: `-m 1` схлопывает влитую ветку в один
коммит, и это почти никогда не то, что нужно.

### 4a. Если коммитов больше одного — одним или по одному

**Выбрано больше одного коммита — не решай сам**, но и отдельным вопросом
не спрашивай: это варианты ответа в подтверждении (шаг 5). Человек часто
хочет, чтобы в чужом репозитории появился один коммит, а не шесть его
черновиков; но так же часто история важна как есть. По вариантам видно,
что именно приедет:

- **по одному** (по умолчанию) — сколько выбрали, столько и приедет, каждый
  со своим сообщением;
- **одним коммитом** (`--squash`) — вся серия сворачивается в один, сообщения
  собираются подряд; своё сообщение задаётся `--message "..."`.

Предложи и текст сообщения, если выбрано схлопывание: собранная простыня
из шести черновиков обычно хуже одной осмысленной строки. Показывай её
человеку до `apply`, а не после.

Спрашивать не нужно, когда: коммит один; человек сам сказал «одним коммитом»
или «как есть»; в конфиге стоит `squash = true` и он про это знает —
тогда просто скажи, каким режимом идёшь.

Схлопывание живёт поверх обычного переноса: конфликты, пауза и `continue`
работают ровно так же, серия сворачивается в самом конце. Но `abort` посреди
squash-серии оставит уже применённые коммиты **по отдельности** — это не
поломка, просто сворачивать было ещё нечего.

### 5. Показать сухой прогон

```bash
git-xfer plan -p <профиль> --to <a|b> --commits <выбор>
```

Рабочее дерево не трогается, грязное дерево и невыгруженная ветка `plan`
не мешают — гони его до stash и `switch`. Покажи человеку результат как
есть: где будут конфликты и в каких файлах, какие коммиты станут пустыми,
каков фактический порядок применения (список идёт newest-first,
применяется наоборот).

**Подтверждение спрашивай здесь — один раз и за всё**: сводка из раздела
«Что выяснить до переноса» плюс результат `plan`, варианты «Да, по одному» /
«Да, одним коммитом» / «Нет, поправить». Ответ «нет» с поправкой — новая
сводка с поправкой и новый вопрос, не кусочный перезапрос.

### 6. Применить — и довести до конца

После «да», без вопросов:

1. stash с меткой, если в цели незакоммиченные правки (1b);
2. `switch` / `switch -c`, если ветка не выгружена (1a);
3. `doctor` — должен дать `0`;
4. `apply`;
5. `switch` обратно на исходную ветку;
6. вернуть правки из stash по метке (1b);
7. итог одним сообщением: что перенесено / пусто / пропущено, где теперь
   HEAD цели, что с незакоммиченными правками.

```bash
git-xfer apply -p <профиль> --to <a|b> --commits <выбор> --yes
# одним коммитом, если человек выбрал так:
git-xfer apply -p <профиль> --to <a|b> --commits <выбор> --yes \
  --squash --message "feat: короткое осмысленное сообщение"
```

`--yes` ставь только после явного «да». Код `0` — дальше по списку (возврат
ветки и правок, итог). Код `3` — конфликт: ветку и stash не трогай, пока
серия не доведена.

**Что приедет в цель по умолчанию:** сообщение коммита без единой приписки
и без строк `Co-authored-by:`; автором и коммиттером становится тот, кто переносит,
author date — момент переноса; коммитов приедет столько же, сколько выбрали.
В коммите git два поля: author (кто написал) и committer (кто применил).
`keep_author = true` возвращает в author автора оригинала с его датой;
committer в любом случае тот, кто переносит, — это git, а не настройка.
Схлопнутому коммиту при `keep_author` достаётся автор первого коммита серии,
а при включённом `trailer` — по трейлеру на каждый вошедший коммит.

Кому нужно иначе — ключи `keep_author`, `keep_coauthors`, `trailer` и `squash`
в конфиге (разово: `--keep-author`, `--keep-coauthors`, `--trailer`,
`--squash`). Что действует сейчас, печатает `git-xfer status` строками
«Сообщение:», «Авторство:»
и «Схлопывание:»; у начатой серии он показывает её собственные опции,
а не конфиг.

Трейлер `(cherry picked from commit ...)` выключен не просто так, и цена
у этого есть: без него «уже переносили» утилита помнит только по своему
state (эта машина) и по patch-id (эвристика `≈`). Если человек удивляется,
что уже перенесённый коммит снова показан как `+` — причина почти всегда
эта: state удалили (`cleanup --state`) или переносят с другой машины.
Сам ничего не включай: скажи, что помогло бы `trailer = true`, и оставь
решение человеку.

## Конфликты

Перенос встал, код `3`. Насколько ты волен чинить его сам — говорит политика
из конфига, её печатает `git-xfer status` строкой `Конфликты: <политика>`.
Разовое указание человека («почини сам», «ничего не трогай») главнее конфига.

| политика | что делаешь |
|---|---|
| `ask` | ничего не правишь: показываешь суть и предлагаешь решение, ждёшь ответа |
| `mechanical` | механические чинишь сам и показываешь что сделал; смысловые выносишь человеку |
| `auto` | чинишь всё сам, включая смысловые, и отчитываешься постфактум |

У профиля с префиксом `git show CHERRY_PICK_HEAD` на паузе покажет
синтетический коммит: сообщение и автор правильные, но родителя из реальной
истории у него нет. Это норма, а не сбитый state — конфликт разрешается как
обычно.

**Что считать механическим.** Обе стороны правили разные строки одного участка;
порядок или набор импортов; отступы и форматирование; сгенерённые файлы
и лок-файлы; добавление разных элементов в один список или словарь; конфликт
целиком в комментариях. Признак простой: **обе правки нужны, и объединить их
можно, не решая, какая из них верна.**

**Что механическим не является — и при `mechanical` уходит человеку.** Две
разные реализации одного и того же; разошедшееся условие или граничный
случай; изменившаяся сигнатура или контракт; правки, где одна сторона
отменяет другую; конфликт, который не понимаешь. **Сомневаешься — значит
смысловой.** Цена ошибки тут — молча закоммиченный неверный код в рабочем
репозитории, и выглядеть это будет как успешный перенос.

Порядок работы:

1. `git-xfer status -p ... --to ...` — на каком коммите встали, сколько
   осталось и какая политика;
2. `git -C <цель> diff --name-only --diff-filter=U` — что конфликтует;
3. прочитай файлы и **пойми оба изменения**. Сообщение переносимого коммита:
   `git -C <цель> log -1 --format=%B CHERRY_PICK_HEAD`. Историю целевой
   стороны файла: `git -C <цель> log -3 --oneline -- <файл>`. В самом файле
   верхняя половина (`<<<<<<< HEAD`) — сторона цели, нижняя — переносимая;
4. дальше по политике. Что бы ни выбрал — **расскажи человеку, что именно
   было в конфликте и как он разрешён**; молча не проходи даже при `auto`;
5. `git -C <цель> add <файлы>`;
6. `git-xfer continue -p <профиль> --to <a|b>` — доведёт коммит и докрутит
   очередь. Серия может встать снова на следующем коммите — это нормально,
   повторяй с шага 2.

Маркеры конфликта (`<<<<<<<`, `=======`, `>>>>>>>`) должны исчезнуть из файла
целиком. Перед `add` проверяй:

```bash
git -C <цель> grep -n '^<<<<<<<\|^>>>>>>>' -- <файл>
```

Пустой вывод и код `1` — маркеров нет, всё в порядке (у `grep` это штатное
«ничего не нашлось», а не ошибка). Любой вывод — файл чинить дальше.

Другие выходы: `git-xfer skip` (пропустить этот коммит, продолжить остальные),
`git-xfer abort` (откатить **только текущий** коммит; уже перенесённые останутся).

Серия закончилась — `continue` вернул `0`, или был `skip`/`abort` на
последнем коммите — доведи хвост из шага 6: ветку обратно, правки из stash,
итог. Про stash на паузе не забывай: он ждёт именно этого момента.

Чего не делать:
- **не зови `cleanup --state`, чтобы «отвязаться» от проблемы** — это забывает
  незавершённую серию, оставляя репозиторий как есть. Только по явной просьбе;
- не трогай `git cherry-pick --abort` руками, когда серию ведёт `git-xfer` —
  у него свой `abort`, который не сносит уже разрешённое;
- не двигай HEAD между паузой и `continue` — утилита это заметит и откажется
  гадать, и будет права.

## Если что-то не работает

| симптом | причина и что делать |
|---|---|
| `git: 'xfer' is not a git command` | утилиты нет в `PATH` — см. раздел 0 |
| `command -v git-xfer` молчит после симлинка | `~/.local/bin` не в `PATH`, скажи человеку |
| `attempted relative import with no known parent package` | запустили файл пакета напрямую; нужно `python3 -m gitxfer` или `bin/git-xfer` |
| `нужен Python 3.11 или новее` | `python3` в `PATH` старый; ставить через `uv`/`pipx` или звать `python3.11 -m gitxfer` |
| `FileNotFoundError` из `os.getcwd()` | каталог, где стоит терминал, удалён или переехал — сделай `cd` в существующий |
| `конфиг не найден` | `git-xfer init` и заполнить, либо работать через `--source`/`--target` |
| `не описан ни один профиль` | шаблон создан, но профили не вписаны |
| код `2` на `doctor` | репозиторий не готов; причина в выводе, разбери с человеком |

Не понял, что случилось, — **загляни в журнал**, он для этого и заведён.

## Когда что-то непонятно — журнал

```bash
git-xfer status -p <профиль> --to <a|b>   # покажет путь
tail -80 ~/.local/state/git-xfer/git-xfer.log
```

Там каждый вызов git с кодом возврата и временем, каждый шаг серии и ошибки
с трейсбеком. Это первое место, куда смотреть при коде `4` и при любом
«почему оно так себя повело».

## Обратное направление

Та же пара, другой `--to`.

**С трейлером** (`trailer = true`) перенесённое видно с обеих сторон: запись
лежит в самой целевой истории, поэтому обратный список честно помечает такие
коммиты `−`, и по кругу они не гоняются.

**Без трейлера — а это сейчас по умолчанию** — обратное направление их так
не узнаёт: маппинг в state заведён на целевой репозиторий того переноса,
который уже случился, и при смене направления не читается. На обратном пути
такие коммиты покажутся `≈` (совпал patch-id), а не `−`. Это не сбой:
скажи человеку, что помечать их `−` тут нечем, и что `≈` при переносе
почти наверняка станет пустым коммитом и будет отброшен. Сам ничего
не переноси «на всякий случай».

## Разовые ветки — без правки конфига

```bash
git-xfer list -p <профиль> --to b -b feature/login          # обе стороны
git-xfer list -p <профиль> --to b --source-branch feature/x # только источник
git-xfer list --source <путь> --target <путь> -b master     # вовсе без конфига
```

Флаг про одну сторону вторую не трогает: с профилем ветка второй стороны
берётся из конфига.

## Чего делать нельзя

- запускать `apply` без явного согласия человека на конкретный набор коммитов;
- обходить `doctor`, который вернул код `2` прямо перед `apply`;
- разрешать смысловой конфликт молча, если политика не `auto`;
- оставлять маркеры конфликта в закоммиченном файле;
- переносить коммиты «на всякий случай», которых он не просил;
- добавлять `--include-skipped` без явного «да» на конкретный коммит с `×`;
- коммитить в ветку, которую человек не выбирал, — ветка из конфига сама
  по себе согласием не является;
- переключать или создавать ветку в рабочем репозитории, не назвав этого
  в подтверждении переноса; и не вернуть потом исходную;
- доставать из stash не своё: только запись с меткой `git-xfer autostash`,
  никаких голых `stash pop`, `stash drop` чужих записей, `stash clear`;
- прятать правки через `reset --hard`, `checkout -- .` или `--force` вместо
  stash; ставить `stash -u` без просьбы;
- коммитить вернувшиеся из stash правки — они остаются незакоммиченными;
- оставить правки человека в stash и не сказать об этом;
- выдумывать `a_prefix`/`b_prefix` за человека, если проект явно лежит
  в подкаталоге, а в профиле про это ничего нет.
